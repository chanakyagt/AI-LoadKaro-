01Platform at a Glance

LoadKaro is a two-sided freight marketplace for the Indian road-logistics market. Shippers post loads that need moving; truck owners post the availability of their vehicles. The platform surfaces each side to the other, records expressions of interest, and hands off to a phone call for the actual negotiation. A moderation layer verifies the identity of users and the documentation of vehicles.

Business modelMarketplace / discovery — not a 3PL
Matching mechanismBrowse → call (tel:) + interest record
Runtime surfaces3 (mobile, dashboard, backend)
BackendSingle Supabase project
Primary authPhone OTP (mobile) · Email+password (staff)
Application tables11 in public schema
User roles5 (shipper, truck_owner, broker, moderator, admin)
Languages shipped4 (EN, हिन्दी, ಕನ್ನಡ, తెలుగు)

The five defining architectural decisions

DecisionWhat it meansConsequence
Single shared backend Both client applications point at one Supabase project — one Postgres database, one auth provider, one storage bucket. No service-to-service API layer exists between the apps. The database schema is the integration contract.
Two different trust postures Mobile uses the anon key and is fully governed by Row Level Security. The dashboard uses the service_role key on server-only routes and bypasses RLS entirely. Mobile security lives in the database; dashboard security lives in application code. Two separate enforcement systems must stay in agreement.
Phone-first identity Marketplace users authenticate only by SMS OTP. Email/password is reserved for staff. Removes password friction for the target user, but couples user acquisition to SMS deliverability and Indian DLT registration.
No realtime, no push All discovery is pull-based: the user opens a list screen and it queries. No WebSocket subscriptions, no push notifications. Simple and cheap. Freshness depends on the user re-opening a screen; there is no server-initiated re-engagement channel.
Call-based matching The platform does not broker, price, or escrow. It opens a tel: link and writes an interests row. Minimal liability and regulatory surface; the interests table is the only telemetry available for measuring marketplace liquidity.

Value chain in one line

Shipper posts load→ Truck owner browses→ Interest recorded→ Phone call→ Deal off-platform
Truck owner posts availability→ Shipper browses→ Interest recorded→ Phone call
Either side uploads KYC / RC→ Moderator reviews in dashboard→ verified / rejected

05Connection Contracts

"How it's connected" is best understood as four distinct contracts. Each has its own credential, its own enforcement point, and its own failure mode.

5.1 Contract A — Mobile ↔ Supabase (direct, RLS-governed)

PropertyDetail
Client constructionA single module-level client in LoadKaro/lib/supabase.js. There is exactly one client instance in the app; every screen imports it.
CredentialsEXPO_PUBLIC_SUPABASE_URL + EXPO_PUBLIC_SUPABASE_ANON_KEY (falling back to the legacy EXPO_PUBLIC_SUPABASE_KEY). Both are compiled into the bundle and are public by design.
Session handlingstorage: AsyncStorage, autoRefreshToken: true, persistSession: true, detectSessionInUrl: false. Sessions survive app restarts.
Transport hardeningA custom fetch wrapper aborts any request after 30 seconds unless the caller supplied its own signal. This exists specifically for users on stalled 2G connections, where the socket stays open but no data flows.
Degraded modeIf env vars are missing, isSupabaseConfigured is false and a placeholder client is constructed against https://placeholder.supabase.co so the app fails at the request level rather than crashing at import.
Query styleDirect PostgREST calls with embedded joins and .range() pagination at PAGE_SIZE = 20. No client-side cache — every screen re-queries on focus.
Failure modeAn RLS mismatch is silent on reads: forbidden rows are simply absent from the result set, so a policy regression reads as "no data" rather than an error.

5.2 Contract B — Dashboard browser ↔ Next.js server

PropertyDetail

Because there are no migration files and no generated types wired into either app, adding an enum value in the database will not produce a compile error anywhere; it will surface as an unlabelled value in the UI. 06Identity & Authentication

Both applications authenticate against the same auth.users table, but through different methods and with different post-login resolution.

6.1 Mobile — phone OTP

Two modes share one OTP screen. Register collects name, phone, and role up front and passes them as auth metadata; Sign in collects only the phone number.

  1. The screen normalizes the number via formatPhoneOtpIndia() — strips non-digits, accepts 10-digit, 91-prefixed 12-digit, or 0-prefixed 11-digit input, validates the national part against /^[6-9]\d{9}$/, and emits E.164 +91XXXXXXXXXX.
  2. supabase.auth.signInWithOtp({ phone, … }) triggers the SMS.
  3. The user enters six digits; verifyOtp({ phone, token, type: 'sms' }) returns a session.
  4. syncUserAfterOtp() reconciles auth.users with public.users: on register, if no profile row exists it inserts one (id, name, phone, role); it then selects the full profile.
  5. resolveDashboardRoute() maps role to a navigator via config/roleRoutes.ts.
  6. The Zustand store receives { user, session, dashboardRoute }, and RootNavigator — keyed on dashboardRoute — remounts into the correct experience.

Session lifecycle

  • initializeAuth() runs on mount: getSession(), fetch the public profile if a session exists, set isReady, then install an onAuthStateChange listener.
  • The listener debounces its profile fetch by 400 ms to avoid racing the profile INSERT that registration performs moments earlier.
  • If a profile fetch fails but a user is already in state, the existing user is preserved — transient network errors do not log the user out.
  • signOut() clears Supabase state, clears the store, and resets the route to the default.
Operational dependency Mobile sign-up and sign-in are entirely dependent on SMS delivery. In the Indian market this means DLT registration of the sender entity, header, and templates. No fallback authentication method (email, magic link, WhatsApp) exists in the app, so an SMS outage is a total outage of new-user acquisition and of any user without a live session.

6.2 Dashboard — email and password

  1. signInWithPassword({ email, password }) against the browser anon client.
  2. Immediately after, the page reads role from public.users for that user id.
  3. admin → /admin/dashboard; moderator → /moderator/dashboard; anything else → forced signOut() plus a "not authorized" message. A marketplace user who somehow knows a dashboard URL cannot hold a session there.
  4. Every subsequent request is re-checked by middleware and again by requireDashboardAccess() inside each route handler.

Moderator provisioning

Moderators are created by an admin through a two-step OTP flow rather than by password invitation: POST /api/admin/moderator/send-otp (validates the phone, rejects duplicates with 409, sends an OTP) followed by POST /api/admin/moderator/create (verifies the OTP, then either upgrades the existing users row to moderator or inserts a new row already marked verified). New inserts write a create_moderator audit entry.

6.3 Development bypass

For local work without real Supabase Auth users, DASHBOARD_BYPASS_AUTH (server) and NEXT_PUBLIC_DASHBOARD_BYPASS_AUTH (client) short-circuit both gates. The role is read from an lk-bypass-role cookie, defaulting to admin, and requireDashboardAccess() returns { ok: true, bypass: true, userId: null } — which means audit rows written in bypass mode have a null actor.

Production hazard With bypass enabled, anyone who can reach the dashboard origin has full service_role-backed access to every record. These flags must be absent — not merely false — in every production environment, and should be part of the deployment checklist.

Availability overlap prevention — stopping a truck being double-booked across two date windows — is enforced only in the client, by a query performed before insert. It is not a database constraint, so a concurrent double submission can defeat it.

7.5 Index strategy

Roughly 41 indexes support the two dominant access patterns. Marketplace browsing is served by route-and-date composites (idx_loads_route_date over origin, destination, loading date), a partial index on open loads only (idx_open_loads WHERE status = 'open'), and status/date indexes on availabilities. Ops screens are served by created_at DESC composites on audit_log, interests, and the verification tables — matching the dashboard's default newest-first sort.

08Core Data Flows

8.1 Posting a load (shipper)

  1. The post screen loads the locations reference data for state and city pickers.
  2. The shipper fills route, loading date, required truck category, capacity, and payment terms.
  3. The client derives advance_percentage from payment_type — 100 for advance, the user's figure for partial_advance, NULL for after_delivery — mirroring the database CHECK so the insert cannot be rejected for that reason.
  4. INSERT INTO loads with posted_by = auth.uid(); status defaults to open.
  5. An admin_alerts row is created for the load, surfacing it on the admin alerts screen.
  6. The shipper is returned to their loads list.

8.2 Browsing and expressing interest (either side)

The market list screens issue a single PostgREST query with embedded joins — pulling the poster's name and phone and both location rows in one round trip — filtered by route and date, ordered newest first, and paginated with .range() at 20 rows per page. Two actions are available on each card:

ActionEffectNotes
CallLinking.openURL('tel:' + phone) Hands off to the device dialer. The platform records nothing about the call — no duration, no outcome, no confirmation it happened.
Show InterestINSERT INTO interests Writes load_id or availability_id, interested_by, contacted_party, and status = 'interested'. This is the platform's only liquidity signal.

8.3 Posting availability (truck owner)

  1. Load the owner's own trucks plus the location reference data.
  2. Owner selects a truck, an origin, up to two preferred destinations, and a date window.
  3. Client-side validation rejects an inverted range or a start date in the past.
  4. An overlap query checks for an existing availability on the same truck covering those dates.
  5. INSERT INTO availabilities with status = 'available'.

8.4 Verification — the one flow that crosses both applications

This is the only workflow where a mobile action is completed by a dashboard action. It is therefore the most important interconnection in the platform.

Mobile — submit
1 · Pick documents
  • Truck: RC, insurance, licence, fitness
  • User (individual): Aadhaar, PAN, DL, other ID
  • User (organization): GST, company PAN, incorporation, trade licence
2 · Create submission
  • INSERT verification_submissions
  • Returns submission.id
3 · Upload files
  • Per file: URI → blob → arrayBuffer
  • Storage upload to the scoped path
↓ INSERT verification_documents (batch)  ·  UPDATE entity SET verification_status = 'pending' ↓
Dashboard — review
4 · Queue
  • Users and trucks with verification_status = 'pending'
5 · Inspect
  • GET /verification/submissions
  • GET /verification/documents
  • POST /verification/signed-url → 300 s URL
6 · Decide
  • POST /verification/decision
  • Updates entity + submission
  • Writes review_verification audit row

The decision handler performs two sequential updates — the entity's verification_status, then the submission's status, review_decision, reviewed_at, reviewed_by, and any rejection_reason — followed by a fire-and-forget audit write. The two updates are not wrapped in a transaction, so a failure between them would leave the entity and its submission disagreeing.

Back on mobile, the user's "My Documents" view reads their most recent submission and its document rows, and opens each file through a 300-second signed URL generated by the anon client. A rejected user can resubmit, which creates a new submission and returns the entity to pending.

8.5 Dashboard record operations

Every ops screen is the same CommonDataTable component pointed at a different table. It reads through the single generic GET /api/admin/data endpoint and writes through PATCH /api/admin/row, which means adding a new ops screen requires no new API surface — only a column configuration. Inline verification changes are permitted directly from the grid when the current status is pending or unverified.

10.5 Injection surface

The one place user-controlled text reaches PostgREST's query grammar is the select parameter of GET /api/admin/data, which must support embedded joins. It is defended by a character allowlist (/^[\w\-,.*! ():]+$/) and an 8 000-character cap; sort columns are restricted to /^[\w]+$/. Everywhere else, values pass through the Supabase client's parameterized builders.

12.3 Shared-env bridge

next.config.ts maps EXPO_PUBLIC_SUPABASE_URL, _ANON_KEY, and _KEY onto their NEXT_PUBLIC_ equivalents, and the middleware falls back to the EXPO_PUBLIC_ names when the Next ones are unset. A single .env can therefore serve both applications during development. This convenience must not be extended to the service-role key, which has no EXPO_PUBLIC_ counterpart and must never acquire one.

12.4 Environment topology

Single-environment reality There is one Supabase project. No staging or preview project is configured, and no Supabase branch workflow is in use. Combined with the absence of migration files, this means schema and policy changes are made directly against the production database, with safety resting on manual rls_backup_*.sql snapshots kept in the repository root. This is the platform's largest operational risk and the clearest candidate for hardening.

15Architectural Observations

Recorded as findings of the discovery, not as a remediation plan. Severity reflects the risk to the platform, not the effort to address it.

15.1 Structural strengths

  • One backend, one schema. With no service mesh and no inter-app API, there is a single source of truth and a very small operational surface for a team of this size.
  • Defence in depth on the dashboard. Middleware, a per-handler access check, a table allowlist, a per-role column allowlist, unconditional PII stripping, and an audit row — five independent controls in front of a key that bypasses the database's own security.
  • Business rules in the database. The payment/advance logic is a CHECK constraint, so no client bug can produce a load with incoherent payment terms.
  • One generic data endpoint. Every ops screen reuses /api/admin/data and CommonDataTable, so the audited attack surface stays constant as screens are added.
  • Field-realistic engineering. The 30-second fetch timeout, the offline banner, the 400 ms auth-listener debounce, and four Indian languages are all responses to how the target user actually connects.

15.2 Findings

#FindingSeverityDetail
1Production is the only environmentHigh One Supabase project, no migrations, no staging, no branch workflow. Schema and RLS changes are applied live, with only manual SQL snapshots as a rollback path.
2Enum definitions triplicatedHigh Postgres, lib/schema/enums.ts, and the mobile label configs must be edited together. Nothing enforces it; drift surfaces as unlabelled values in production UI. Generated types exist as a Supabase capability but are not wired into either build.
3Bypass flags are a live production hazardHigh A single stray environment variable converts the dashboard into an unauthenticated, service_role-backed interface to the entire database.
4Directory-wide readabilityMedium OR true in the user and truck SELECT policies lets any authenticated account enumerate all users — names and phone numbers included — and all vehicles. Necessary for the marketplace to function as designed, but it is an open scraping surface.
5Verification decision is not transactionalMedium Entity status and submission status are two sequential updates. A failure between them leaves them inconsistent, with no reconciliation process.
6Audit trail is best-effortMedium Fire-and-forget writes mean a mutation can succeed with no audit record. For a log intended to support compliance, this weakens the guarantee it exists to provide.
7No error or usage telemetryMedium No crash reporter and no analytics on either surface. A mobile crash in the field is invisible; funnel questions can only be answered by querying the database directly.
8Availability overlap enforced client-side onlyMedium A pre-insert query, not a constraint. Concurrent submissions can double-book a truck.
9Single-channel authenticationMedium SMS OTP is the only way into the mobile app. An SMS or DLT disruption is a total acquisition outage with no fallback path.
10Two UI generations coexistLow Redesigned navigators for shipper and truck owner sit alongside the legacy stack that still serves brokers. The truck-owner navigator imports the shipper's tab bar, and tab state is local component state that resets on remount.
11No document retention policyLow Superseded KYC files persist in the bucket indefinitely. A policy decision, but one with data-protection implications given what the bucket holds.
12Dead schema objectsLow load_rate_visibility_enum is referenced by no column; subscription_type is populated but unused by any feature.
13No CI and no automated testsLow No test runner or workflow configuration is committed. Every change is validated manually, which compounds findings 1 and 2.
